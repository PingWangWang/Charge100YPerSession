# 西安交警「交通违法随手拍」自动化 — 设计文档

> 文档状态：**方案已确定** —— GKD 订阅自动 + 车牌人工填写。本文档涵盖需求理解、技术调研、最终方案、实施方案、测试方案与使用方案。

## 1. 项目概述

**目标**：在安卓手机上，用户手动打开微信小程序「西安交警」后，通过 **GKD 订阅规则** 自动完成「交通违法随手拍 → 违停行为上报」中可确定化的点击与输入流程；号牌信息由用户核对后手动填写，最终由用户手动提交。

**技术形态**：本仓库为 GKD 订阅模板（TypeScript + pnpm），最终通过 `pnpm run build` 生成 `dist/gkd.json5` 订阅文件，供 GKD 加载。

**运行环境**：Android + GKD（建议 ≥ v1.12.0，以支持滑动动作）+ 微信 App。

**关键词**：GKD / 订阅规则 / 微信小程序 / webview 文本识别 / 无障碍 / 半自动。

---

## 2. 需求理解

### 2.1 业务目标

用户每次随手拍举报违停车辆时，需手动重复「随手拍 → 立即上报 → 同意须知 → 违停行为 → 填表」等大量点击与输入，十分繁琐。希望自动化这些固定动作，减少重复操作；车牌信息由用户确认后填写。

### 2.2 使用场景与入口

- 入口：用户**手动打开**微信小程序「西安交警」并进入首页后，自动化开始。
- 入口说明：不依赖桌面图标自动唤起；自动化起点是「已进入小程序」。

### 2.3 约束条件

- 平台：Android。
- 主体：微信小程序（运行于微信 `com.tencent.mm` 内部）。
- 能力边界：GKD 订阅为静态规则，**无**图片识别（OCR）与基于识别结果的动态分支能力。
- 前置依赖：GKD ≥ v1.12.0（滑动）；微信小程序 webview 文本可被无障碍读取（稳定性需真机验证）。

### 2.4 边界范围

**自动化范围**：

- 首页 →「随手拍」
-「交通违法行为」→「立即上报」
- 勾选「我已阅读并同意」→「开始上报」
- 选择「违停行为」
- 填写信息：关闭「注意事项」弹窗、填「问题描述 / 上报位置 / 详细地址」、拍照辅助（部分自动）

**明确不做**：

- 自动识别车牌号码 / 按颜色判断号牌类型（超出 GKD 能力，由用户手动填写）。
- 自动点击「提交」（提交前用户需核对并可能修改）。
- 「违法时间」（系统自动）、「违法视频」（非必填）的填写。

### 2.5 假设

- 车牌号每次变化，需人工确认填写（本方案接受）。
- 微信小程序 webview 文本可被 GKD 匹配（需真机验证）。
- 相机预览「完成」按钮属于微信进程，无需额外全局规则。

## 3. 完整流程拆解（需求澄清结论）

### 3.1 关键固定值

| 字段 | 值 |
|------|----|
| 问题描述 | `路边违停` |
| 详细地址 | `灞桥区元熙樾府小区（绕城高速联络线）` |
| 定位搜索关键词 | `元熙樾府`，选择结果第一条 |
| 号牌类型 | 用户由照片颜色判断：蓝色=小型汽车，绿色=新能源汽车 |
| 车牌号牌 | 用户由照片手动输入 |

### 3.2 分步流程

| 步骤 | 界面 | 自动化动作 | 交互 |
|------|------|-----------|------|
| 1 | 小程序首页（西安交警） | 点击「随手拍」 | 自动 |
| 2 | 交通违法随手拍 | 点击「交通违法行为」→「立即上报」 | 自动 |
| 3 | 用户须知 | 勾选「我已阅读并同意」→ 点击「开始上报」 | 自动 |
| 4 | 违法类型 | 选择「违停行为」 | 自动 |
| 5.1 | 填写违法信息 | 关闭「注意事项」弹窗 → 点「确认」 | 自动 |
| 5.2 | 填写违法信息 | 「问题描述」输入「路边违停」 | 自动 |
| 5.3 | 填写违法信息 | 「上报位置」点「重新选择」→ 输入「元熙樾府」→ 选第一条 → 点「完成」 | 自动 |
| 5.4 | 填写违法信息 | 「详细地址」输入固定地址 | 自动 |
| 5.5 | 填写违法信息 | 拍照辅助 | 半自动 |
| 6 | 填写违法信息 | 用户填「号牌类型」+「车牌号牌」→ 核对 → 点「提交」 | 手动 |

**拍照辅助（5.5）说明**：

1. 先填完文字字段（5.2~5.4），**不要**自动拉起相机。
2. 第 1 张：由**用户点击**「上传照片」#1 → 相机 → 用户手动拍照（角度自定）→ 预览页**自动化点「完成」**。
3. 第 2/3 张：由**自动化点击**「上传照片」#2/#3 → 相机 → 用户拍照 → 预览页**自动化点「完成」**。

## 4. 技术可行性核实（网络调研结论）

- **webview 文本识别**：GKD 基于无障碍服务可读取小程序 webview 文本，社区已有用于关闭小程序广告的先例；但**动态 webview 内容**匹配可能不稳定，建议对 webview 动态内容加 `matchDelay`，并以快照审查确认节点。
- **滚动**：GKD v1.12.0 起支持 `action: 'swipe'`（`direction` + `distance`），可用于滚动到表单下方字段。
- **相机「完成」按钮**：确认属于微信 `com.tencent.mm`，无需额外全局规则。
- **车牌识别**：GKD 订阅无图片识别能力 → 本方案转由用户手动填写。

---

## 5. 方案选型说明

曾评估三套方案：

- **方案一（无障碍脚本 + 车牌 OCR）**：能全自动识别车牌，但**脱离本 GKD 仓库**形态，需新建脚本工程、安装运行环境并接入 OCR API Key。因用户明确要求保留 GKD 订阅形态，**否决**。
- **方案二（GKD 订阅自动 + 车牌人工填写）**：保留本仓库，自动化所有重复动作，车牌由用户手动填。**选定**。
- **方案三（GKD + 剪贴板 OCR）**：链路长、时序与可靠性一般，不如方案二简洁，**否决**。

## 6. 最终方案：GKD 订阅自动 + 车牌人工填写

### 6.1 方案概述

用本仓库的 GKD 订阅自动完成从首页到「详细地址」填写的固定点击/输入/拍照辅助；在号牌字段处**暂停**，交由用户手动填写并自行提交。

### 6.2 文件与模块划分

| 文件 | 职责 |
|------|------|
| `src/apps/com.tencent.mm.ts` | 主流程全部规则（首页→随手拍→立即上报→开始上报→违停行为→填写信息） |
| `src/subscription.ts` | 订阅元信息（`id`、`name`、`author` 改为自定义值） |
| `src/globalGroups.ts` | 预留（相机属微信，本方案暂不配置；如需兜底再加） |
| `src/categories.ts` | 规则分类（按需） |

### 6.3 规则组织

用 group / rule + `order` 编排顺序：

- 首页组：匹配「随手拍 / 西安交警」→ 点击「随手拍」。
- 随手拍组：匹配「交通违法行为 / 立即上报」→ 点击「立即上报」。
- 用户须知组：匹配「用户须知 / 我已阅读并同意」→ 先点「我已阅读并同意」，再点「开始上报」。
- 违法类型组：匹配「违法类型 / 违停行为」→ 点击「违停行为」。
- 填写组：
  - 关闭「注意事项」弹窗 → 点「确认」。
  - 「问题描述」输入「路边违停」。
  - 「上报位置」点「重新选择」→ 搜索框输入「元熙樾府」→ 点第一条结果 → 点「完成」。
  - 「详细地址」输入固定地址。
  - 拍照：第 1 张由用户点「上传照片」，第 2/3 张自动点；每张后自动点相机预览「完成」。

### 6.4 关键选择器与动作

| 目标 | 匹配（文本为主） | 动作 |
|------|----------------|------|
| 随手拍入口 | `text*="随手拍"` | `click` |
| 立即上报 | `text*="立即上报"` | `click` |
| 同意勾选 | `text*="我已阅读并同意"` | `click` |
| 开始上报 | `text*="开始上报"` | `click` |
| 违停行为 | `text*="违停行为"` | `click` |
| 弹窗确认 | `text*="确认"` | `click` |
| 上传照片 | `text*="上传照片"` | `click` |
| 相机预览完成 | `text*="完成"` | `click` |
| 输入字段 | 聚焦后 | `inputText` / `setText` |
| 滚动到下方 | 目标字段未显现时 | `swipe`（direction + distance） |

> 注：`text*="xxx"` 为包含匹配示意；实际选择器需结合快照审查确定更精确的 `id` / `vid` / 结构关系，避免误点。

### 6.5 关键挑战与对策

| 挑战 | 对策 |
|------|------|
| webview 动态内容匹配不稳定 | 加 `matchDelay`；用快照审查锁定节点；必要时用 `id`/`vid` 而非纯文本 |
| 长表单需滚动 | 用 `action: 'swipe'` 逐步滚动，再触发相应字段输入 |
| 页面切换/相机返回时序 | 为关键动作设置 `actionDelay` |
| 重复/误触发 | 用 `activityIds`、`actionMaximum`、`resetMatch` 限制只在目标页面执行 |

## 8. 测试方案

### 8.1 测试环境

- 真机：Android + 微信 + GKD（≥ v1.12.0），授予 GKD 无障碍权限并开启微信规则。
- 对象：从「首页」到「详细地址」填写的完整链路。

### 8.2 测试用例

| 编号 | 场景 | 预期 |
|------|------|------|
| T1 | 页面顺序如常 | 步骤 1~4 全部自动成功 |
| T2 | 填写信息 | 弹窗关闭、问题描述/定位/详细地址按固定值正确填入 |
| T3 | 拍照辅助 | 用户点 #1 后自动点完成；#2/#3 自动拉起并点完成 |
| T4 | 号牌停顿 | 停在号牌字段，不自动填、不自动提交 |
| T5 | 弹窗/提示偶尔出现 | `确认` 规则能处理 |
| T6 | 定位搜索结果顺序变化 | 结果列表第一条可被稳定匹配 |
| T7 | 拍照中断/取消 | 规则可再次触发或安全退出，不误点 |
| T8 | webview 加载慢 | `matchDelay` 生效，不因过早匹配而失败 |

### 8.3 通过标准

- 从首页到「详细地址」全自动成功，拍照辅助正常，且停在号牌字段。
- `pnpm run check`（类型 + 订阅结构校验）通过。

### 8.4 回归与灰度

- 每次改动后执行 `pnpm run check`、`pnpm run build`。
- 先在本地订阅小范围验证，确认稳定后**手动提交**，或自行托管构建产物 `dist/`。

## 9. 使用方案（用户最终如何使用）

1. **安装 GKD**，且升级到 ≥ v1.12.0；授予无障碍权限。
2. **添加订阅**：导入本仓库生成的 `dist/gkd.json5`（或订阅地址）。
3. **开启微信规则**：在 GKD 中启用 `com.tencent.mm` 相关规则组。
4. **每次使用**：
   - 手动打开微信小程序「西安交警」；
   - 自动化自动跑完前半段（到「详细地址」）；
   - 按提示手动点第 1 张「上传照片」并拍照，之后自动化接管第 2/3 张；
   - 到「号牌类型 / 车牌号牌」处**手动填写**并核对；
   - 手动点击「提交」。

**注意事项**：

- 违停举报受理时间为 **7:00~22:00**。
- 需在 **5 分钟内**完成资料提交，超时需重新进入。
- 需开启手机 GPS，以便定位。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| webview 文本匹配失败 | 某步不触发 | 用 `matchDelay`/快照审查；改用 `id`/`vid`；必要时回退为手动完成该步 |
| 页面结构/文案变更 | 规则失效 | 版本化迭代，快照审查回归 |
| 滚动或时序不稳 | 误点/漏点 | 调 `actionDelay`、滑距；限制 `actionMaximum` |
| 车牌信息需人工 | 流程非全自动 | 已接受；保留用户核对点，防止误报 |

---

> 说明：本方案刻意将「车牌自动识别」与「自动提交」排除在自动化之外，既规避 GKD 静态规则的能力边界，也保留了用户在提交前核对的机会。
