# 西安交警「交通违法随手拍」自动化 — 设计文档

> 文档状态：**已落地**。本仓库输出 GKD 订阅（`dist/gkd.json5`，当前版本 **v11**）。本文档描述最终采用并已验证的方案，及其设计原则与使用方式。

## 1. 项目概述

**目标**：在安卓手机上，用户手动打开微信小程序「西安交警」后，通过 **GKD 订阅规则** 自动完成「交通违法随手拍 → 违停行为上报」中可确定化的**点击**动作；文本输入、号牌与最终提交由用户手动完成。

**技术形态**：本仓库为 GKD 订阅模板（TypeScript + pnpm），`pnpm run build` 生成 `dist/gkd.json5` 订阅文件供 GKD 加载，并自动递增订阅版本号。

**运行环境**：
- Android 手机 + 微信 App（`com.tencent.mm`）
- GKD（≥ v1.12.0），并授予 **Shizuku 强制模拟点击** 权限（用于 `clickCenter` 坐标触摸）
- 手机已开启定位，且在受理时段内（违停 7:00~22:00）

**关键词**：GKD / 订阅规则 / 微信小程序 / webview / 无障碍 / 坐标模拟点击 / 半自动。

## 2. 需求理解

### 2.1 业务目标

用户每次随手拍举报违停，需重复「随手拍 → 立即上报 → 同意须知 → 违停行为 → 填表 → 拍照 → 提交」等大量操作。希望自动化其中机械重复的**点击**动作，减少手动操作量；文本与号牌由用户在关键节点确认填写。

### 2.2 使用场景与入口

- 入口：用户**手动打开**微信小程序「西安交警」并进入首页后，自动化开始。
- 不负责唤醒小程序；起点是「已进入小程序首页」。

### 2.3 约束条件

- 平台：Android。
- 主体：微信小程序（运行于微信 `com.tencent.mm`）。
- 能力边界：GKD 订阅为静态规则，**无**图片识别（OCR）与基于识别结果的动态分支能力。
- 前置依赖：GKD ≥ v1.12.0；Shizuku 提权以支持 `clickCenter` 强制模拟点击；小程序 webview 文本可被无障碍读取。

### 2.4 边界范围

**自动化（仅点击类）**：
- 首页 →「随手拍」
-「交通违法行为」→「立即上报」
- 勾选「我已阅读并同意」→ 点「开始上报」
- 选择「违停行为」
- 填写信息：关闭「注意事项」弹窗（点「确认」）
- 拍照辅助：第 2/3 张「上传照片」自动拉起，相机预览页自动点「完成」

**手动（交由用户完成）**：
- 文本输入：问题描述（`路边违停`）、详细地址、定位搜索词（`元熙樾府` → 选第一条）
- 号牌类型（蓝牌=小型汽车、绿牌=新能源汽车）与车牌号牌
- 最终「提交」按钮

### 2.5 假设

- 车牌号每次变化，需人工确认填写（本方案接受）。
- 微信小程序 webview 文本可被 GKD 无障碍读取（已真机验证）。
- 相机预览「完成」按钮属于微信进程，可在微信规则内处理。

## 3. 完整流程拆解

### 3.1 手动固定值

| 字段 | 值 |
|------|----|
| 问题描述 | `路边违停` |
| 详细地址 | `灞桥区元熙樾府小区（绕城高速联络线）` |
| 定位搜索关键词 | `元熙樾府`，选择结果第一条 |
| 号牌类型 | 用户由照片颜色判断：蓝色=小型汽车，绿色=新能源汽车 |
| 车牌号牌 | 用户由照片手动输入 |

### 3.2 分步流程

| 步骤 | 界面 | 自动化动作 | 交互 |
|------|------|-----------|------|
| 1 | 小程序首页（西安交警） | 点击「随手拍」 | 自动 |
| 2 | 交通违法随手拍 | 点击「交通违法行为」卡片（即立即上报） | 自动 |
| 3 | 用户须知 | 勾选「我已阅读并同意」→ 点击「开始上报」 | 自动 |
| 4 | 违法类型 | 选择「违停行为」 | 自动 |
| 5.1 | 填写违法信息 | 关闭「注意事项」弹窗 → 点「确认」 | 自动 |
| 5.2 | 填写违法信息 | 问题描述输入 `路边违停` | 手动 |
| 5.3 | 填写违法信息 | 上报位置：重新选择 → 搜索 `元熙樾府` → 选第一条 → 完成 | 手动 |
| 5.4 | 填写违法信息 | 详细地址输入固定地址 | 手动 |
| 5.5 | 填写违法信息 | 拍照辅助 | 半自动（见下） |
| 6 | 填写违法信息 | 号牌类型 + 车牌号牌 + 核对 + 提交 | 手动 |

**拍照辅助（5.5）**：

1. 先由用户填完流程文字字段（5.2~5.4）与号牌，**不要**自动拉起相机。
2. 第 1 张：用户手动点「上传照片」#1 → 相机（用户自行调整角度）→ 预览页**自动点「完成」**。
3. 第 2/3 张：**自动化**点击「上传照片」#2/#3 → 相机（用户拍照）→ 预览页**自动点「完成」**。

> 说明：第 1 张由用户点，是为了给用户主动权；第 2/3 张由自动化接管。自动化的「上传照片」规则以 `preKeys` 绑定相机「完成」，确保不会抢在用户拍照前触发。

## 4. 技术可行性核实（含真机结论）

- **webview 文本识别**：GKD 基于无障碍服务可读取小程序 webview 文本，但动态内容匹配需轮询窗口，已通过 `matchTime/forcedTime` 主动轮询验证。
- **webview 合成按钮**：小程序内的「交通违法卡片」「开始上报」「确认」等为 webview 合成的 `clickable=true` 节点，**不响应**无障碍 `ACTION_CLICK`（`click`），需用 `clickCenter`（坐标模拟触摸）并配合 Shizuku 强制模拟点击，才能生效。这是本方案最关键的踩坑结论。
- **页面切换**：微信小程序在同 Activity 内跳页不触发无障碍事件，需用 `matchTime/forcedTime` 轮询窗口。
- **残留节点**：小程序跳页后旧 webview 节点会残留在无障碍树中，需用 `actionMaximum:1 + resetMatch:'match'` 限制只在目标界面执行一次。
- **滚动**：GKD v1.12.0 支持 `swipe`，但本方案文本字段由用户手动填写，**暂未使用滑动**；未来若改为自动输入再引入。
- **车牌识别**：GKD 订阅无图片识别能力，转由用户手动填写。

## 5. 方案选型

候选方案：

- **方案A（GKD 自动点击 + 人工填写）**：保留本仓库形态，自动化所有确定化点击，文本与号牌由用户手动。**选定**。
- **方案B（无障碍脚本 + 车牌 OCR）**：需脱离 GKD 仓库、新建脚本工程并接入 OCR API，违反保留 GKD 订阅形态的诉求，**否决**。
- **方案C（GKD + 剪贴板 OCR）**：链路长、时序与可靠性一般，不如方案A简洁，**否决**。

## 6. 最终方案：GKD 自动点击 + 人工填写

### 6.1 方案概述

用 GKD 订阅自动完成从首页到拍照辅助的可确定化**点击**；在文本输入与号牌字段前**暂停**，交由用户手动填写并核对，最终由用户手动提交。

### 6.2 文件与模块划分

| 文件 | 职责 |
|------|------|
| `src/apps/com.tencent.mm.ts` | 主流程全部规则（首页→随手拍→立即上报→开始上报→违停行为→填写信息→拍照） |
| `src/subscription.ts` | 订阅元信息（`id: 233300`、`name: 西安交警-违停上报助手`、`author` 等） |
| `src/categories.ts` | 规则分类（当前为空） |
| `src/globalGroups.ts` | 全局规则（当前为空，相机属微信进程无需兜底） |

### 6.3 规则组织（当前实际规则）

单个 group（`key: 0`）内以 `order` 编排顺序，全部规则均开启 `matchRoot: true`：

| key | 名称 | 匹配 | 动作 |
|-----|------|------|------|
| 101 | 首页-点击随手拍 | `[text="随手拍"][visibleToUser=true]` | `click` |
| 102 | 随手拍页-点击立即上报 | `Button[text!=""][clickable=true][visibleToUser=true] + @Button[clickable=true][visibleToUser=true]` | `clickCenter` |
| 103 | 用户须知-勾选我已阅读并同意 | `[text="我已阅读并同意"][visibleToUser=true]` | `click` |
| 104 | 用户须知-点击开始上报 | `[text="开始上报"][visibleToUser=true]`（`preKeys:[103]`） | `clickCenter` |
| 105 | 违法类型-选择违停行为 | `[text="违停行为"][visibleToUser=true]` | `click` |
| 106 | 填写信息-关闭弹窗(确认) | `[text="确认"][visibleToUser=true]` | `clickCenter` |
| 110 | 拍照-点击上传照片(第2/3张) | `[text="上传照片"][visibleToUser=true]`（`preKeys:[111]`，`actionMaximum:2`） | `click` |
| 111 | 相机预览-点击完成 | `[text="完成"][visibleToUser=true]`（`actionMaximum:3`） | `click` |

### 6.4 关键实现要点

| 要点 | 说明 |
|------|------|
| 通用结构锚定（rule 102） | 目标「交通违法卡片」文字是无障碍树中的图片渲染、不含 text；改用「唯一带文本且可点击的用户卡片」`Button[text!=""]` 取其紧邻后置兄弟 Button。不绑定用户名，换账号仍有效；结构关系不依赖绝对像素，换机型仍命中。 |
| `clickCenter` | webview 合成可点击按钮（交通违法卡片/开始上报/确认）不响应无障碍 `click`，用坐标模拟触摸并配合 Shizuku 强制模拟点击绕过小程序防御。 |
| 主动轮询 | 微信小程序同 Activity 跳页不触发无障碍事件，后续规则统一加 `matchDelay:300`、`matchTime:6000`、`forcedTime:4000`、`actionDelay:200` 轮询窗口。 |
| 防残留重复触发 | 每条自动化规则 `actionMaximum:1 + resetMatch:'match'`，旧 webview 节点残留时不会重复执行、也不会跨页误点。 |
| 拍照时序 | rule 110 以 `preKeys:[111]` 绑定相机「完成」先完成一次，确保第 1 张由用户主动点、第 2/3 张才由自动化接管。 |

## 9. 使用方案

1. **安装 GKD**（≥ v1.12.0）并授予无障碍权限；通过 Shizuku 授予**强制模拟点击**权限。
2. **添加订阅**：导入 `dist/gkd.json5`（或订阅地址）。
3. **开启微信规则**：在 GKD 中启用 `com.tencent.mm` 规则组。
4. **每次使用**：
   - 手动打开微信小程序「西安交警」，自动化自动跑完点击链路；
   - 到文本字段，用户手动填写问题描述/定位/详细地址；
   - 手动点第 1 张「上传照片」并拍照，随后自动化接管第 2/3 张与相机「完成」；
   - 手动填写并核对号牌类型与车牌号，手动点「提交」。

**注意事项**：
- 违停举报受理时间为 **7:00~22:00**。
- 需在 **5 分钟内**完成资料提交，超时需重新进入。
- 需开启手机 GPS，以便定位。
- 若某一步未触发（尤其 webview 合成按钮），优先更新订阅到最新版本，并确认 Shizuku 提权生效。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| webview 合成按钮不响应 `click` | 某步点了但无效 | 改用 `clickCenter` + Shizuku 强制模拟点击 |
| 小程序同 Activity 跳页不触发事件 | 后续步骤不评估 | 用 `matchTime/forcedTime` 主动轮询窗口 |
| 旧 webview 节点残留 | 重复触发/误点 | `actionMaximum:1 + resetMatch:'match'` |
| 页面结构/文案变更 | 规则失效 | 版本化迭代，快照审查回归 |
| 账号/机型变化 | 锚定失效 | 用 `Button[text!=""]` 通用结构锚定，不绑定姓名与绝对像素 |
| 车牌信息需人工 | 流程非全自动 | 已接受；保留用户核对点，防止误报 |

---

> 说明：本方案刻意将「文本输入」「车牌自动识别」与「自动提交」排除在自动化之外，既规避 GKD 静态规则的能力边界，也保留用户在提交前的必要核对与主动权。
